# 팀 코드 규칙

**아래 스택 표에 있는 것만 쓴다.** 새 라이브러리·기술을 넣고 싶으면 이슈로 먼저 묻는다.
발표 때 팀원 모두가 설명할 수 있어야 하기 때문이다. **화면과 코드 꼴은 수업(Spring 노션) 그대로**다. 수업에서 "확장"으로만 짚고 넘어간 것(Spring Data JPA, Spring Security, SSE)은 기능에 꼭 필요해 쓰고 있으니, 맡은 사람이 [역할 분담](05-역할분담.md)의 "설명 정리"로 팀에 풀어 준다.

## 1. 스택

| 무엇 | 쓰는 것 | 왜 |
|---|---|---|
| 백엔드 | Spring Boot 4, Java 17, Gradle | 수업 기준. 팀원 JDK 가 17·21·25 여도 `release 17` 로 컴파일 |
| DB 접근 | Spring Data JPA (엔티티 + Repository) | 표 9개와 관계가 많아 SQL 을 손으로 쓰면 고칠 곳이 많다 |
| DB | H2(로컬, 설치 없음) / Postgres(배포) | 로컬은 받자마자 실행되게, 배포는 무료 호스팅이 되는 것 |
| 로그인 | Spring Security + 카카오 OAuth2, 세션 쿠키 | 비밀번호를 우리가 저장하지 않는다 |
| 실시간 | SSE(`SseEmitter`) | 서버 → 화면 한쪽 알림만 필요해서 WebSocket 보다 단순 |
| 화면 | Thymeleaf + HTML5 · JavaScript · jQuery(`$.ajax`) | 수업 기준. 서버 하나(`:8080`)로 화면과 API 를 같이 띄운다 |
| 도구 | IntelliJ, IntelliJ HTTP Client 또는 Talend API Tester, ERD 는 `docs/03-DB설계.md` 의 mermaid | |

## 2. 폴더와 층

```
src/main/java/com/tripmate/
  user/     로그인(AppUser, SecurityConfig, KakaoUserService, LoginPageController)
  trip/     여행방·참여자·초대·SSE(Trip, Member, TripController, TripPageController, TripEvents)
  survey/   설문(SurveyController, SurveyService, SurveyPageController)
  role/     역할·배정·추천 알고리즘(RoleController, RoleService, RolePageController)
  stay/     숙소·투표·링크 미리보기(StayController, StayPageController)
src/main/resources/
  templates/   화면. fragments/common.html(공통 head·방 머리), <기능>/*.html
  static/js/   화면 JS. common.js(api·loadTrip·listen) + 화면마다 하나
  static/css/  style.css 하나
```

- **기능별 패키지** 안에 Controller, Service, Repository, 엔티티, Dto 를 같이 둔다. 한 기능을 한 사람이 맡으니 자기 폴더만 보면 된다
- 컨트롤러는 둘로 나눈다(수업의 `UserPageController` / `UserController` 처럼)
  - `XxxPageController`(`@Controller`): 템플릿 이름만 돌려준다. 계산·DB 없음
  - `XxxController`(`@RestController`, `/api/**`): JSON 을 주고받는다
- 요청 흐름: 화면 컨트롤러 → 템플릿 → jQuery `$.ajax` → `/api/...` → Controller → Service → Repository → DB. 발표 때 이 순서로 설명한다
- Controller 에 계산을 쓰지 않는다. 한 층은 한 가지 일. (지금 일부 Controller 에 계산이 있다 → 각자 Service 로 옮기는 것이 1주 차 일)
- 의존성은 생성자로 받는다: `private final TripRepository tripRepository;` + 생성자
- 방 API 는 처음에 `tripAccess.me(tripId)`(참여자인지), `self(...)`(본인인지), `host(...)`(방장인지)를 부른다

## 3. 코드 꼴

```java
// GET: /api/trips/1
@GetMapping("/trips/{tripId}")
@Transactional(readOnly = true)
public ResponseEntity<TripDto.Response> getTrip(@PathVariable Long tripId) {
    var me = tripAccess.me(tripId);
    var trip = tripRepository.findWithMembersById(tripId)
            .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
    return ResponseEntity.ok(TripDto.Response.of(trip, me));
}
```

- 메서드 위에 **부르는 예 한 줄**(`// GET: /api/trips/1`), 받는 JSON 이 있으면 그 예도 한 줄
- 주석은 **왜**만 쓴다. 코드가 이미 말하는 것(`// 방을 찾는다`)은 쓰지 않는다
- 칸만 있는 그릇은 `record`(요청·응답 Dto). getter/setter 를 손으로 쓰지 않는다. JPA 엔티티는 클래스 + 필요한 getter 만
- 타입이 오른쪽에 보이면 `var`
- 숫자를 박지 않는다: `private static final int REQUIRED_BONUS = 100;`
- 이름은 한 뜻에 한 이름. `data`, `info`, `payload` 를 섞지 않는다
- 알면서 남긴 한계는 `// shortcut: <한계>, <언제 고칠지>` 로 적는다
- `System.out.println`, `console.log` 는 확인용. PR 올리기 전에 지운다

## 4. 주소(URI) 규칙

| 하지 말 것 | 이렇게 |
|---|---|
| `GET /api/trips/delete/1` | `DELETE /api/trips/1` |
| `/api/Trips`, `/api/trip_members` | 소문자, 하이픈: `/api/trips`, `/api/trip-members` |
| `/api/trip` 목록 | 복수 명사: `/api/trips` |
| `/api/trips?id=1` 로 한 개 | 식별은 경로 `/api/trips/1`, 검색·페이지는 쿼리 |

- 데이터는 모두 `/api/**` (JSON). 화면 주소는 `XxxPageController` 의 `@GetMapping` 이다
- 새 주소를 만들면 [URL 설계](04-URL설계.md) 표에 한 줄 더한다

## 5. 응답과 화면

- 응답: `ResponseEntity.status(HttpStatus.CREATED).body(dto)`. 조회 200, 생성 201, 삭제 204, 로그인 안 함 401, 권한 없음 403, 없음·남의 방 404, 동시에 바꿈 409
- 요청 검사는 Dto 에 `@Valid` + `@NotBlank`·`@Size`·`@Min` 같은 것으로, 들어오는 문에서 한 번
- 바깥 응답(카카오, 숙소 페이지)은 필요한 칸만 꺼내 내 그릇에 담는다. 통째 `Map` 으로 들고 다니지 않는다
- 사용자가 넣은 값은 템플릿에서는 `th:text`, jQuery 에서는 `.text()` 로만 넣는다. `th:utext`·`.html(값)` 은 쓰지 않는다(XSS). 바깥 주소는 `https://` 만 `<img src>` 에 넣는다
- API 는 `common.js` 의 `api(method, url, body)` 로 부른다. 401 이면 로그인 화면으로 보내 준다
- 함수 위에 부르는 API 를 한 줄로 적는다: `// PUT: /api/trips/1/votes/2  { "stayId": 3 }`

## 6. DB

- 엔티티 이름은 단수 CamelCase, 표는 snake_case(자동). `user` 는 예약어라 `AppUser` → `app_user`
- 관계는 `@ManyToOne(fetch = LAZY)`. 목록에서 관계를 같이 읽을 때는 `@EntityGraph` 로 한 번에(N+1 금지)
- "한 사람 한 표"처럼 규칙은 DB 유일 제약으로도 막는다(`@UniqueConstraint`)
- 동시에 같은 것을 고치는 곳은 `@Version`(낙관적 락)
- 표를 바꾸면 [DB 설계](03-DB설계.md)의 ERD 도 고친다
- 비밀값(카카오 키)은 `secrets.properties`(gitignore)에. 저장소에 올리지 않는다

## 7. 테스트

- 기능을 고치면 `./gradlew test` 가 통과해야 PR 을 연다
- 새 API 는 MockMvc 테스트 하나 이상. 로그인은 `TestLogin.as(mvc, "민지")` 로
- 새 화면을 만들면 `PageTest` 에 한 줄 더한다(템플릿이 오류 없이 그려지는지)

## 8. 발표 준비

- 각자 `docs/parts/<GitHub아이디>.md` 를 자기 기능 기준으로 채운다(틀은 `docs/parts/_틀.md`)
- 자기 기능의 요청 하나를 골라 브라우저 → 화면 → Controller → Service → Repository → DB → 화면 순서로 말할 수 있어야 한다
- 코드 위치는 파일 경로와 메서드 이름으로 적는다

## 리뷰에서 걸러낼 것

- 모든 메서드에 붙는 긴 설명 주석, 코드를 되풀이하는 주석
- 한 번만 부르는 작은 메서드 여러 겹, 쓰지 않는 인자, "나중에 쓸지도" 만든 클래스
- 모든 줄을 감싼 try-catch, 로그만 찍고 삼키는 예외
- 영어·한국어 주석 섞기. 주석은 짧은 한국어
